La última posta: ponerlo en internet

El motor ya está armado y probado. Lo que falta es que cualquiera lo pueda usar sin que tu computadora esté prendida — y esa parte te la dejamos a propósito.

Por qué esta parte es tuya

Todo lo que hay en packages/core —el cálculo del combo, la sustitución cuando algo no tiene stock— está construido, testeado y andando. Eso resolvía si la idea se sostenía técnicamente. Ya sabés que sí.

Deployarlo es otra cosa: es la parte donde un proyecto deja de ser "funciona en mi compu" y pasa a ser algo real. Es también, casi siempre, la parte donde más se aprende — y donde más trabas aparecen. Por eso te la dejamos entera.

El modelo mental antes de tocar nada

Tenés dos piezas independientes, y hoy las dos viven en tu computadora.

packages/web
El front
hoy: tu compu, puerto 5500
→
packages/api
La API
hoy: tu compu, puerto 3001

Para que funcione para cualquiera, cada pieza tiene que vivir en un servidor real, y el front tiene que saber la dirección real de la API — no localhost, que solo existe dentro de tu propia máquina.

El orden que conviene seguir

Cada paso depende del anterior — no te conviene saltear ni cambiar el orden.

1

Elegí dónde va a vivir la API

Necesitás un servicio que corra packages/api de forma continua. Hay varios con plan gratuito para proyectos chicos — cada uno organiza distinto un repo con varias carpetas (esto se llama "monorepo"), así que fijate cómo le indicás cuál es la carpeta de arranque.

Para investigar"deploy node express monorepo root directory" + el nombre del servicio que elijas.
2

Deployala y anotá la URL real que te da

Una vez arriba, vas a tener algo como https://tu-proyecto.algo.app. Probala directo con /health en la barra del navegador antes de seguir — si eso no responde, nada de lo que viene después va a andar.

La GEMINI_API_KEY es opcional. Sin ella, el sistema sigue funcionando con reglas fijas en vez de IA real. No hace falta que se la pidas a nadie para que esto funcione.

3

Hacé que el front sepa esa URL sin tenerla escrita fija

Buscá ENDPOINT en packages/web/app.js. Hoy apunta a localhost:3001 a mano. Necesitás que ese valor cambie según dónde esté corriendo la página — local o ya deployada — sin que tengas que editar el código cada vez que redeployás.

Para investigar"runtime config static site" — hay más de una forma correcta de resolver esto, la idea es que entiendas el problema, no que copies una solución.
4

Deployá el front apuntando a la API real

packages/web son archivos estáticos — HTML, CSS, JS sin build. Es la parte más simple de las dos de deployar. El resultado te va a dar otra URL, esta sí para compartir.

5

Probalo como lo probaría alguien que no sos vos

Abrí la URL del front en el celular, o pedile a alguien que lo abra desde su casa. Armá un combo de verdad. Si algo falla acá y no te había fallado en local, es casi siempre el paso 3.

Una trampa real que ya nos comimos por vos

Ya corregido en el repo

loadCatalog() en packages/api/src/app.ts leía el catálogo con fs.readFileSync sobre una ruta armada en el momento. Andaba perfecto en local. En un servidor tipo serverless se hubiera roto en silencio, porque esas plataformas arman el paquete a deployar siguiendo los import del código — no rastrean qué archivos abre fs mientras corre.

Lo cambiamos por un import estático del JSON, que sí queda incluido siempre. No te lo cuento para que lo copies — ya está arreglado. Te lo cuento porque es un tipo de bug que vas a volver a pisar con otros archivos si no tenés el patrón general en la cabeza: lo que tu código lee en tiempo de ejecución no siempre viaja con el deploy; lo que importa arriba, sí.

Cuando algo no funciona

El orden en que atacás un error importa tanto como el error en sí.

  • 1Leé el mensaje de error completo, no el resumen que le harías vos de memoria dos minutos después.
  • 2Buscalo tal cual está escrito, entre comillas. La mayoría de los errores de deploy ya los pisó alguien más.
  • 3Si después de un rato buscando seguís sin entender qué te está pidiendo la plataforma, ahí sí preguntá — con el error completo a mano, no "no me anda".

Para ir tildando

  • API deployada, /health responde desde su URL real (no localhost)
  • Front lee la URL de la API de forma configurable, no hardcodeada
  • Front deployado, apuntando a la URL real de la API
  • Probado desde un dispositivo que no es tu compu de siempre
  • Armaste un combo de verdad y salió bien
